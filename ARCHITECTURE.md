# Офис программистов — архитектура

Команда агентов-разработчиков под управлением из единого центра. Модель —
по образцу Palantir: сила не в количестве агентов, а в том, что **все изменения
проходят через один аудируемый шлюз с тирами риска и одобрением человека**.

## Главный инвариант

> Агент не исполняет действия. Он только **предлагает** Действие из каталога
> онтологии. Тир риска и легальность определяет **онтология**, а не агент.
> Шлюз — тонкий неподкупный исполнитель политики.

Из этого следует всё остальное: агенты сменяемы, контроль живёт в чокпоинте,
а политику видно глазами в командном центре, а не только в коде.

## Пять примитивов

1. **Онтология** (`ontology.yaml`) — единственный источник правды: объекты,
   тиры риска, каталог Action Types, штат с полномочиями.
2. **Шлюз / Action Service** (`action_service.py`) — единственный путь мутации.
   Определяет тир из онтологии, проверяет полномочия, ведёт провенанс, держит
   очередь на одобрение.
3. **Агенты** (`agents.py`, `dispatcher.py`) — читают онтологию, предлагают
   действия. Диспетчер Kristina маршрутизирует задачу одному исполнителю.
4. **Исполнитель** (`executor.py`) — стоит строго за шлюзом, заперт в корне
   проекта на ноутбуке. Каждый Action Type → одна ограниченная операция.
5. **Командный центр** (`web/`) — оперативный экран: задачи, очередь одобрений,
   провенанс, штат, политика.

## Путь запроса

```
Человек ставит задачу (центр)
   │  POST /office/task
   ▼
Kristina (dispatcher) ── маршрутизирует ──► Агент-исполнитель
                                               │  выбирает одно действие
                                               │  POST /actions/propose
                                               ▼
                                         Шлюз (Action Service)
                                          1. действие в онтологии?      нет → 422
                                          2. у агента есть полномочия?   нет → 403
                                          3. тир из онтологии
                                               │
                            ┌──────────────────┴───────────────────┐
                     requires_approval=false              requires_approval=true
                            │                                       │
                            ▼                                       ▼
                   Исполнитель (в корне проекта)           Очередь pending
                            │                          человек одобряет в центре
                            ▼                                       │
                      провенанс (SQLite) ◄──────────────────────────┘
```

Любой исход — `executed` / `pending` / `rejected_*` / `failed` — попадает в
провенанс и виден в AuditLog.

## Компоненты бэкенда

| Файл               | Роль |
|--------------------|------|
| `ontology.yaml`    | объекты, тиры, Action Types, штат и полномочия |
| `action_service.py`| шлюз: propose / approve / reject / pending / audit; тир и полномочия из онтологии; провенанс в SQLite |
| `executor.py`      | `LocalExecutor` (заперт в `WORKSPACE_ROOT`) и `StubExecutor` (dry-run без него) |
| `agents.py`        | `Agent` (только propose, без execute) + клиент шлюза + реестр штата |
| `dispatcher.py`    | Kristina: LLM-роутер + fallback по ключевым словам |
| `llm.py`           | OpenAI-совместимый клиент (AITunnel/DeepSeek), ключи из env; `FakeLLM` для тестов |
| `office_server.py` | HTTP-фасад: `/office/task`, `/office/tasks`, `/office/agents`, `/office/ontology`; журнал задач |

## Тиры риска

| Тир      | Одобрение | Примеры действий |
|----------|-----------|------------------|
| AUTO     | нет       | read_file, search_code, lint |
| LOW      | нет       | run_tests, create_branch |
| MEDIUM   | нет       | (зарезервирован) |
| HIGH     | **да**    | write_file, commit, merge_pr, delete_branch |
| CRITICAL | **да**    | force_push, deploy, rotate_secret |

Запись файлов и коммиты — HIGH: каждое изменение проекта сначала проходит через
человека. Менять тир — одна строка в `ontology.yaml`, код не трогается.

## Командный центр (`web/`)

Секции для `kristina_agent_center/app/src/` (стиль сохранён, данные живые):
`Dashboard` (счётчики), `Tasks` (постановка + журнал маршрутизации),
`Approvals` (очередь HITL), `AuditLog` (провенанс), `Agents` (штат),
`Ontology` (зеркало политики). Клиент — `web/api.ts`.

## Безопасность

- Исполнитель заперт в `WORKSPACE_ROOT`; выход за корень → отказ.
- Нет действия «произвольный shell»: каждый Action Type — конкретная команда,
  git вызывается argv-списком (без shell-интерполяции).
- Полномочия проверяются на шлюзе (неподкупно), не только на стороне агента.
- Ключи — только в env, никогда в коде.
- Деструктивные действия (deploy, force_push, rotate_secret) намеренно не
  привязаны к исполнителю — бросают ошибку, а не делают опасное молча.

## Запуск

```bash
cd office
python -m pytest -q                    # 29 тестов

export WORKSPACE_ROOT=~/Projects/syndi-vercel   # подключение к проекту
export TEST_CMD="npm test"  LINT_CMD="npm run lint"
export LLM_BASE_URL=...  LLM_API_KEY=...  LLM_MODEL=...   # AITunnel

uvicorn action_service:app --port 8000  # шлюз + исполнитель
uvicorn office_server:app  --port 8100  # офис (Kristina)
# в app/: npm run dev                    # центр на :5173
```

Без `WORKSPACE_ROOT` исполнитель работает как заглушка (ничего не пишет на диск).
Подробнее о запуске и таблице возможностей исполнителя — в `web/RUN.md`.
